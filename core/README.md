# wkp (Rust core)

The Rust implementation of WKP, shared by every binding. `no_std` (needs `alloc`), no
dependencies. The wire format is specified in `../SPEC.md`.

## API

All functions write into caller-provided buffers (cleared first), so reusing the same `Vec`s or
`Frame` across calls avoids reallocating.

```rust
use wkp::{decode_f64, decode_geometry, decode_header, encode_f64, encode_geometry, Frame};

// Geometry with a header: LINESTRING (38.5 -120.2, 40.7 -120.95, 43.252 -126.453) at 5dp.
let coords = [38.5, -120.2, 40.7, -120.95, 43.252, -126.453];
let mut out = Vec::new();
encode_geometry(2 /* LINESTRING */, &coords, 2, 5, &[1], &[3], &mut out)?;
assert_eq!(out, b"@DAA_p~iF~ps|U_ulLnnqC_mqNvxq`@");

let mut frame = Frame::default();
decode_geometry(&out, &mut frame)?;
assert_eq!(frame.coords, coords);
assert_eq!((frame.group_segment_counts, frame.segment_point_counts), (vec![1], vec![3]));

// Headerless float streams, one precision for all dimensions or one per dimension.
encode_f64(&coords, 2, &[5], &mut out)?;
let mut values = Vec::new();
decode_f64(&out, 2, &[5], &mut values)?;
```

Topology is flat: `segment_point_counts` gives the points in each ring/linestring/point, and
`group_segment_counts` the segments in each polygon/part. See `bindings/c/README.md` for how each
geometry type maps onto it.

Errors are `Error::InvalidArgument` (bad arguments: inconsistent counts, dimensions outside
1..=16, precisions outside 0..=63, non-finite values or |value × 10^precision| ≥ 2^58) and
`Error::MalformedInput` (the encoded data isn't valid WKP).

## Compatibility with the C implementation

Output is byte-for-byte identical to the C core that preceded this crate (0.5.x) for all valid
inputs; `tests/golden.rs` checks 600 vectors generated by it, including corrupted inputs. The only
differences are for inputs the C core handled badly:

- non-finite values, values too large to encode losslessly, and precisions outside 0..=63 are
  rejected rather than producing garbage
- chars above `~` (126) are rejected while decoding
- a geometry header with 0 or more than 16 dimensions is an error (the C core divided by zero or
  overran a stack buffer)

## Performance notes

- Encoding builds each value's chars in a `u64` (spreading 5-bit groups into bytes with shifts
  and masks) and stores them with one unaligned write.
- Decoding reads 8 bytes at a time, finds every value terminator in the word at once, and gathers
  the 5-bit groups back with shifts and masks. Blocks advance a fixed 8 bytes, so the next load
  never waits on the current one. Deltas are then prefix-summed and scaled in a second pass.
- The per-dimension loops are specialised for 1–4 dimensions.
- Rounding is `llround`-compatible but done with plain arithmetic, so it inlines.

Run the benchmark with `cargo run --release -p wkp --example bench`.

## Tests

```sh
cargo test -p wkp
```

- unit tests in `src/lib.rs`
- `tests/golden.rs`: compatibility with the C implementation
- `tests/reference.rs`: the optimised decoders against a naive decoder written from `SPEC.md`,
  on random and adversarial input, plus encode round trips
- `tests/fixtures.rs`: the shared fixtures in `data/integration_tests` (also run by every binding)
